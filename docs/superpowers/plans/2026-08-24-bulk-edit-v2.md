# Bulk Edit V2 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Let users touch several allowed bulk-edit fields in one atomic save, including description, donation recipient, and same-type chomesh.

**Architecture:** Change the bulk dialog from an exclusive field picker to an independent-field form. Represent the save as a JSON patch whose key presence means "write this field". One new RPC signature and one Tauri handler update apply every requested column in a single transaction.

**Tech Stack:** React 19, TypeScript, Zustand, shadcn Dialog/Drawer, Vitest, PostgreSQL `jsonb`, Tauri/SQLite.

## Global Constraints

- No new dependency.
- Dedicated branch `feat/bulk-edit-v2`. Do not add this to PR #397.
- One atomic write per save. Never loop two single-field RPCs.
- Untouched fields must not appear in the patch and must not change in the database.
- Existing blockers remain: `initial_balance` (transactions), `completed` (recurring).
- Recurring `status` stays rejected.
- Cancel preserves selection; successful save clears it.
- RTL/LTR, variant locking, pending guards, and loaded-only selection stay unchanged.
- Code, comments, and commit messages in English. Conventional Commits, short.

- [ ] **Step 3: Add the forward migration**

Preconditions: current four-argument updaters exist and jsonb overloads do not.

Do **not** drop the live `(uuid, uuid[], text, text)` signatures. Create the jsonb overloads with the same invoker/search_path/auth guard/lock/exact-count pattern as `20260824114314_limit_bulk_update_text_values.sql`.

Validate `p_updates`:

- `jsonb_typeof(p_updates) = 'object'`
- `p_updates <> '{}'::jsonb`
- keys ⊆ `{payment_method, category, description, recipient, is_chomesh}`
- text lengths: description ≤ 100; payment_method, category, recipient ≤ 50
- if `category` present: homogeneous income or expense family
- if `recipient` present: every locked row is `donation` or `non_tithe_donation`
- if `is_chomesh` present: every locked row has the same type and that type ∈ `{income, donation, recognized-expense}`; value is boolean. Plain `expense` is rejected because balances ignore `is_chomesh` unless the type is `recognized-expense`.

Single `UPDATE` using key presence:

```sql
SET
  payment_method = CASE
    WHEN p_updates ? 'payment_method' THEN p_updates->>'payment_method'
    ELSE transaction_row.payment_method
  END,
  -- same pattern for category, description, recipient
  is_chomesh = CASE
    WHEN p_updates ? 'is_chomesh' THEN (p_updates->>'is_chomesh')::boolean
    ELSE transaction_row.is_chomesh
  END,
  updated_at = now()
```

Reapply `OWNER TO postgres` and the least-privilege EXECUTE grants. Postconditions: V1 four-argument signatures remain, jsonb signatures exist, auth guard present, no `status` write, description length guard present.

- [ ] **Step 4: Implement Tauri and TypeScript callers**

Change both handlers from `field: String, value: Option<String>` to `updates: serde_json::Value` (object). Apply the same validation, then one `UPDATE` with dynamic `SET` clauses built from an allowlist. Never interpolate user keys into SQL; map known keys to literals.
